# Архитектура: авто-получение сессии (кук/токена) для WebSocket-прокси

## Идея в двух словах

Мы хотим избавиться от ручного шага "зайди на сайт, залогинься, открой devtools, скопируй куки/токен".
Вместо этого между пользователем и целевым сервисом ставится прокси, который **сам терминирует TLS-сессию**
и поэтому автоматически видит куки/токен в момент логина — без всякой магии с поддельными сертификатами.

Это не классический MITM с подменой CA-сертификата и warning'ами в браузере. Это TLS-terminating прокси
(TLS offload), просто применённый к процессу логина конкретного человека.

---

## Часть 1. Локальный сервис (клиентская сторона)

```
Браузер юзера --HTTP--> локальный сервис (127.0.0.1:PORT) --HTTPS--> целевой сайт
```

Как это работает:

1. Локальный сервис поднимает страницу логина на `127.0.0.1:PORT` и отдаёт её браузеру **по обычному HTTP**.
   Браузеру не нужно ничего одобрять — это просто локальная страница, TLS тут вообще не участвует.
2. Сам локальный сервис при этом — полноценный **TLS-клиент** к реальному сайту: именно он устанавливает
   HTTPS-сессию с целевым сервисом, забирает у него HTML страницы логина и отдаёт браузеру уже расшифрованным.
3. Пользователь вводит логин/пароль в этой странице — форма уходит на локальный сервис (по HTTP, это ок,
   трафик не покидает машину), а сервис пересылает данные на реальный сайт уже по HTTPS.
4. Сайт отвечает `Set-Cookie` / токеном — их получает **сервис**, потому что именно он был стороной,
   установившей TLS-сессию. Это и есть автоматический перехват кук.
5. Страница закрывается, куки/токен сохранены — пользователь не делал руками ничего лишнего.
6. Дальше локальный сервис использует эти куки/токен, чтобы открыть WebSocket к таргету, и отдаёт
   клиенту готовый локальный канал `ws://127.0.0.1:PORT`.

### Почему нет warning'ов о сертификатах

Браузеру никогда не показывается HTTPS вообще — только чистый HTTP-контент. Поэтому не нужен свой
корневой CA-сертификат в системе и не будет предупреждений о недоверенном сертификате.

### Главная техническая сложность здесь — не TLS, а переписывание контента

Раз сайт отдаётся не под своим доменом, а под `127.0.0.1:PORT`, нужно аккуратно обработать:

- **Абсолютные ссылки и редиректы** на `https://target.com/...` внутри HTML — их нужно переписывать
  на лету на адрес прокси, иначе браузер уйдёт мимо него.
- **JS-запросы** (`fetch`, `XHR`) к `https://target.com/api/...` — пойдут напрямую, мимо прокси. Более того,
  так как страница отдана по HTTP, браузер заблокирует такие запросы как **mixed content**.
- **CSP-заголовки** сайта могут блокировать ресурсы с "неправильного" origin.
- **CSRF-токены**, привязанные к Origin/Referer, или **WebAuthn/passkeys** (жёстко привязаны к origin) —
  сломаются, потому что origin страницы теперь другой.
- **2FA / капча** ломают автоматизацию в принципе, так как это заранее не предсказуемый ручной шаг.

## Часть 2. Серверная часть ("TLS in TLS")

```
Клиент --WSS/HTTPS--> наш сервер --HTTPS--> целевой сервис
```

Та же логика, но с обеих сторон HTTPS:

1. Наш сервер терминирует входящее TLS-соединение от клиента (обычное HTTPS/WSS до нашего сервера).
2. Параллельно сервер сам выступает TLS-клиентом и открывает новое HTTPS-соединение к целевому сервису,
   проходя тот же процесс логина, что и в локальной части.
3. Целевой сервис отвечает `Set-Cookie` / токеном — сервер их перехватывает, так как сам был инициатором
   этого TLS-соединения.
4. После получения сессии этот "логин-воркер" может завершать работу — сессия/токен уже сохранены.
5. Дальше основной сервис держит эту сессию и от имени пользователя проксирует WebSocket-соединение
   до целевого сервиса.

Это стандартный паттерн TLS termination + re-encrypt to backend (как делает, например, nginx),
просто применённый не к произвольному трафику, а конкретно к процессу логина.

## Итоговая схема целиком

```
[Браузер юзера]
      | HTTP (без TLS, локально)
      v
[Локальный сервис 127.0.0.1:PORT]  <-- TLS-клиент --> [Целевой сайт: логин, куки/токен]
      |
      | куки/токен передаются на сервер
      v
[Наш сервер]  <-- TLS-клиент (свой логин-флоу) --> [Целевой сервис: получение сессии]
      |
      | сессия сохранена, воркер логина завершает работу
      v
[Наш сервер держит WS-сессию] <---> [Целевой сервис: WebSocket]
      ^
      | WSS/HTTPS
      |
[Клиент подключается к нашему серверу]
```

## На что стоит обратить внимание

- **Терминология**: точнее называть это не "MITM", а **login relay / TLS-terminating proxy** —
  так меньше путаницы с классическим MITM (подмена сертификатов, pinning и т.д.), которого тут нет.
- **Безопасность**: форма логина на `http://127.0.0.1`, куда пользователь вводит пароль от стороннего
  сервиса — по механике это то же самое, что фишинговая форма, только с благими намерениями и локально.
  Стоит подумать, как и где хранятся полученные креды/токены на сервере, особенно если сервисом
  будут пользоваться не только "свои".
- **ToS целевого сервиса**: автоматический логин и проксирование WebSocket через перехваченные куки,
  скорее всего, не соответствует условиям использования таргета — это юридический риск, который
  стоит явно проговорить и оценить перед реализацией.
- **Ограничения**: 2FA, капча, certificate pinning на стороне клиента таргета (если это не браузер,
  а нативное приложение) — всё это может сломать автоматизацию, и придётся закладывать fallback
  на ручной ввод.
